# Plano da próxima versão — "Instalar e começar"

> **Sobre o número.** Esta missão chegou com o rótulo `v1.1.0`. Ele não é alcançável: a string
> `1.1.0` não existe no repositório, nunca houve um `1.0.0` de nada, o core declara `0.1.0` e a
> extensão `0.2.0-alpha.1` — número que veio de ser a *segunda* missão da extensão, não de semver.
> Pular para `1.x` afirmaria API pública estável enquanto `main` sequer contém a extensão. Este
> plano chama o corte de **`0.3.0`**, alinhando core e extensão numa versão só, e reserva `1.0.0`
> para quando o `apiVersion` do formato de mission estiver congelado. Ver §12.
>
> Base factual: auditoria de código em `feature/DA-VSCODE-MVP-002` (`5bb6a17`), 2026-09-03.
> Nada aqui foi copiado de relatório antigo sem confirmar no código.

## 1. Tese de produto

A capacidade central foi provada em uso local controlado. Onboarding e recuperação ainda não são
produto.

As duas afirmações são verificáveis. A primeira: `PRODUCT-READINESS.md` registra execução real com
fornecedor real, revisão independente real, integração, recovery e dogfooding — o produto alterou o
próprio código; e registra também o tamanho da amostra, oito tentativas com um fornecedor, sem
inventar taxa. A segunda: para usar a extensão é preciso clonar o monorepo, compilar, linkar a CLI
no `PATH` e rodar `agentic init` num terminal; o projeto que o `init` entrega, se executado como
está, **falha**; e uma falha de aquisição de workspace deixa uma task em `READY` para sempre, sem
motivo na tela.

A próxima versão não adiciona capacidade. Ela fecha a distância entre "o produto executa trabalho
real" e "outra pessoa consegue chegar até lá". É uma versão de **caminho de entrada**, e a
extensão VS Code é a porta.

## 2. Estado atual

**O que está provado** (`docs/product/PRODUCT-READINESS.md`): leitura e compilação de missão,
escalonamento, isolamento por worktree, execução real com Claude Code, task gate, revisão
independente real, integração, recovery, dashboard, SSE, pause/resume, dogfooding. A extensão
atingiu o MVP e uma alpha do VSIX foi publicada como pré-release.

## 3. Dor do usuário

Ordenada pelo que acontece na primeira hora de alguém que não escreveu o produto.

**P1 — O projeto que o `init` entrega falha.** O template escreve `providers.default: mock`
(`apps/cli/src/templates.ts:53-60`), e o registry montado a partir dele não injeta `script`
(`packages/providers/src/registry.ts:213-226`), então o mock cai no passo de fallback
(`packages/providers/src/mock.ts:75-78`), não escreve arquivo nenhum, e a observação mede zero
arquivos → `NO_CHANGES` (`packages/orchestrator/src/engine/observe.ts:81-86`) três vezes →
`BLOCKED`. Nada na mensagem liga a causa ao provider de ensaio.

**P2 — Sem `.gitignore`, o planejamento se recusa a gravar.** O `init` não escreve `.gitignore`
nenhum (`apps/cli/src/commands/init.ts:46-51`), embora `ARCHITECTURE.md:408` afirme que esses
caminhos são ignorados. Num projeto externo, `.agentic/state.db-wal` e `-shm` ficam não
rastreados; o observador do repositório hasheia todo arquivo não rastreado
(`packages/orchestrator/src/engine/control-plane.ts:471,517-560`) e o planejamento compara a
impressão digital antes e depois da chamada do planner: mudou, recusa com
`PLANNER_FAILED: o repositorio mudou durante o planejamento`
(`application/planning.ts:311,403-411`). Depois do primeiro run é pior: o `hash-object` encontra a
worktree aninhada, sai diferente de zero, a digital vira indefinida e o planejamento é recusado já
na entrada. **A porta de entrada da extensão tende a falhar em projeto externo.**

**P3 — O VSIX sozinho não serve para nada.** A extensão é cliente puro e o VSIX tem 15 arquivos,
sem CLI e sem módulo nativo. Antes de ele ser útil: Node ≥ 22, `git clone` do monorepo (tudo é
`private: true`, não há artefato publicável), `npm ci`, `npm run build` (o entrypoint importa
`../dist/index.js`), `npm link` — porque num projeto que não é o monorepo os dois primeiros
caminhos de busca nunca existem (`extensions/vscode/src/core/toolchain.ts:228,230`) — e depois
`agentic init` num terminal, porque a extensão não tem comando de init.

**P4 — Falha real do executor chega sem causa.** Quando a CLI do fornecedor falha de verdade
(versão velha, quota, modelo inválido), a frase que o usuário lê é
`AGENT_ERROR: agente encerrou com status failed` (`packages/orchestrator/src/engine/observe.ts:31`).
A causa real existe em `claims.detail` (`packages/providers/src/local-cli.ts:266`) e no arquivo de
log da tentativa. O painel oferece abrir esse log
(`apps/web/src/components/TaskDetailPanel.tsx:654`), mas **o resumo da falha não diz a causa**: o
usuário precisa saber que existe um log e ir buscá-lo. O planner já faz o certo, levando a última
linha da CLI para a própria mensagem (`packages/providers/src/planner.ts:1060-1069`). O executor não
recebeu esse conserto.

**P5 — Preso em silêncio, com a tela dizendo que está tudo bem.** Falha de `workspace-acquired`
grava `policy.invalid_transition`, aplica cooldown de 2 s e mantém a task em `READY`
(`packages/orchestrator/src/engine/orchestrator.ts:1937-1961`). `READY` conta como progresso
(`packages/domain/src/task-run.ts:22-29`), então o run nunca é considerado travado
(`packages/domain/src/run-machine.ts:44-48`) e a UI diz *"pronta — aguardando vaga"*
(`apps/web/src/lib/waiting.ts:206-209`). Na `DA-UX-001` isso rendeu 3.053 eventos sem um único
despacho. Continua vivo: a branch de tentativa preservada por `release(…, 'keep')` — o caminho de
toda saída não-feliz — faz o segundo run da mesma mission bater em
`branch … esta em uso por outra worktree` (`packages/workspace/src/repo.ts:159-164`) a cada tick,
para sempre. Não há comando de limpeza no produto.

**P6 — O provider `mock` pode ser eleito revisor real** (U12, aberta desde a `DA-UX-001`):
a tentativa morre em `AGENT_ERROR: revisor nao emitiu veredito` e queima o orçamento de tentativas.

## 4. Objetivo da 0.3.0

**Instalar a extensão, abrir um repositório e chegar a um run real sem terminal e sem clonar o
produto.**

O critério não é uma lista de features: é uma pessoa que nunca viu o repositório conseguir, em
menos de quinze minutos e sem ler documentação obrigatória, sair de "abri uma pasta" até "tenho uma
mission planejada, aprovada e com pelo menos um despacho real observado", com mensagens que dizem o
que fazer quando algo falha.

**Dois pré-requisitos ficam declarados, não escondidos:** Node ≥ 22 e uma CLI de agente já
autenticada. O produto não instala nem autentica nenhum dos dois — é *subscription-first* por
princípio (P17). O que a versão promete é que, faltando qualquer um, a extensão diga isso na
primeira tela, com o conserto nomeado, em vez de falhar adiante.

## 5. Não-objetivos

Fora desta versão, por decisão explícita: chat próprio (a conversa livre continua no Claude Code e
no Codex), Marketplace, colaboração em equipe, nuvem, telemetria, dashboard corporativo, multi-root
sofisticado, JetBrains, orquestração remota, control plane distribuído, edição do DAG por
arrastar, permissões de organização. Também fora: hardening sem dor observada, micro-refactor e
teste novo sem defeito real por trás.

## 6. Epics

### EPIC 1 — Linha principal e verificação independente
Promover a branch de trabalho para `main` por PR, inaugurando o fluxo; empurrar o commit local
pendente; CI mínima que espelha o perfil `mission` do `gates.yaml` (`verify` + `test:e2e`) em
`push` e `pull_request`; proteção de branch exigindo o check. Sem isso, todo o resto é planejado
sobre uma linha que não contém o produto e que nada verifica.

### EPIC 2 — O primeiro run não mente
`init` escreve `.agentic/.gitignore` (P2); os gates deixam de presumir npm — hoje o template escreve
`npm run lint`, `npm run test` e `npm run verify` fixos (`apps/cli/src/templates.ts:79-87`) enquanto
o produto se anuncia agnóstico de linguagem, então o `init` passa a detectar os comandos reais do
projeto ou a perguntá-los, e nunca a inventá-los; template deixa de entregar `mock` como executor padrão
quando há CLI real observada, e nomeia a troca quando não há (P1); `mock` deixa de ser elegível
como revisor real (P6); o `AGENT_ERROR` carrega a última linha significativa da CLI, mantendo o
código decidido só pelo exit (P4); a sidebar corrige a tabela de estado de provider, que hoje
diverge do contrato (`extensions/vscode/src/vscode/status-view.ts:35-40` mostra `UNKNOWN` onde a
CLI e o dashboard mostram `INSTALLED`).

### EPIC 3 — Instalar sem clonar
Produzir um **runtime relocável**: um tarball autocontido com a CLI, os workspaces internos já
compilados e o dashboard, anexado à release, que a extensão extrai em `globalStorage` na primeira
partida e onde só as dependências externas são instaladas. A detecção atual permanece como caminho
offline.

A ordem importa e foi corrigida pela revisão do plano. Publicar em npm parecia o caminho mais
barato, mas o pacote da CLI hoje não declara `bin`, publica apenas `dist` e depende de workspaces
privados por versão `*` (`apps/cli/package.json`), e o dashboard precisa acompanhar o runtime
(`apps/server/src/config.ts:15`) — ou seja, "publicar" exige de qualquer forma **criar o artefato
relocável primeiro**. O módulo nativo continua sendo resolvido na máquina do usuário, que é o que
importa: `better-sqlite3` usa `prebuild-install` e cai em compilação quando não há binário pronto,
então a instalação local reduz a matriz nativa em vez de nos obrigar a prever plataforma,
arquitetura e ABI. Publicar em npm fica como distribuição adicional, depois, não como pré-requisito
do onboarding.

De brinde conserta um defeito real: a sonda de ABI procura o driver dentro do projeto alvo
(`extensions/vscode/src/core/toolchain.ts:118`), que num projeto externo não existe, e por isso hoje
não verifica nada. Inclui o comando `Agentic: Initialize Project` na extensão, que é o último passo
de terminal obrigatório.

### EPIC 4 — Nunca preso em silêncio
Falha repetida de `workspace-acquired` escala para `BLOCKED` com o motivo do `WorkspaceError`, em
vez de girar para sempre (P5); o motivo de espera na tela lê o último `policy.invalid_transition`
da task; a sidebar mostra `failureReason` nas tasks; um comando de limpeza de worktrees e branches
de tentativa; prazo de stop da extensão maior que o orçamento de drenagem do servidor
(hoje ambos são 30 s, e o cliente estoura primeiro, abortando o restart); a causa real da recusa de
encerramento chega ao toast; e a limitação de Windows passa a ser declarada, porque hoje o sinal
de encerramento é `TerminateProcess` e a prova de grupo morto é uma declaração vazia
(`packages/process/src/runtime.ts:105-109`).

### EPIC 5 — Corte repetível
Uma versão só, propagada por script; remover o nome do VSIX fixo do script `package` — `vsce` já
nomeia o arquivo sozinho — e trocar as três menções literais nos READMEs por link para a última
release; CHANGELOG na raiz; e o processo de release versionado como documento, não como prosa
dentro de um relatório de missão.

A automação de release por tag **fica fora desta versão**: custa mais que quase todo item de
produto e não muda nada para o usuário. Um comando de empacotamento reproduzível mais uma release
manual registrada bastam enquanto o corte for pré-release.

## 8. Plano de lotes

Cada lote entrega algo utilizável e termina com um corte instalável.

A ordem abaixo já incorpora a correção da revisão do plano: começar pela governança do repositório
seria procrastinação disfarçada de fundação, porque nenhum dos itens de maior valor depende
tecnicamente dela.

**LOTE 1 — O primeiro run não mente.** Itens 1, 2, 3, 4, 5, 5b. *Entrega:* quem já tem a CLI
consegue rodar `agentic init` num projeto qualquer, com gates que são os do projeto, e chegar a um
primeiro run real; quando o fornecedor falha, a tela diz por quê. É o menor esforço por unidade de
dor e não depende de nada.

**LOTE 2 — Linha principal e CI.** Itens 6, 7, 8, 21. Empurrar `main`, promover a branch por PR,
CI mínima espelhando o gate `mission`, proteção de branch, nome do VSIX fora do script. *Entrega:*
pela primeira vez `main` contém o produto, e a partir daqui nenhuma mudança entra sem verificação
independente. Vem logo depois do Lote 1 para que os lotes seguintes — os caros — já nasçam
verificados.

**LOTE 3 — Instalar sem clonar.** Itens 9, 10, 11, 12. *Entrega:* a jornada do título — instalar o
VSIX, abrir uma pasta, configurar o projeto pelo editor e executar, sem clonar o monorepo e sem
terminal. É o lote de maior risco, e por isso vem depois de a linha estar verificada e de o
primeiro run já funcionar.

**LOTE 4 — Nunca preso em silêncio.** Itens 13, 14, 15, 16, 17, 18, 19. *Entrega:* toda espera tem
motivo na tela, toda falha tem conserto nomeado, e nenhum estado gira para sempre. Os itens 13, 14
e 16 entram **antes** da primeira alpha: sem eles a alpha entrega um produto que trava em silêncio
na segunda tentativa.

**LOTE 5 — Corte repetível.** Itens 20, 23, mais o corte `0.3.0-beta.1` e a rodada de dogfooding
externo. *Entrega:* a release deixa de ser um procedimento manual descrito em prosa.

## 9. Critérios de aceitação

Por lote, verificáveis, sem porcentagem inventada.

**Lote 1.** Num diretório temporário com `git init` e Node ≥ 22:

- Depois de `agentic init`, `git status --porcelain` lista `.agentic/project.yaml`,
  `.agentic/gates.yaml` e a mission de exemplo — que **devem** ser versionados — e **não** lista
  `.agentic/state.db*`, `.agentic/control-plane.json`, `.agentic/control-plane.lock.db*`,
  `.agentic/runs/` nem `.agentic/worktrees/`.
- Num projeto cujos gates não são npm, o `gates.yaml` gerado contém os comandos informados ou
  detectados, e nenhum `npm run` que o projeto não tenha.
- Rodando a mission de exemplo com o template recém-criado, o run alcança `COMPLETED` com um
  provider real; e com o `mock` explicitamente escolhido, a recusa nomeia o provider de ensaio em
  vez de `NO_CHANGES` genérico. O critério é o evento e o texto, não a inferência de causa.
- Um provider `inprocess` declarado como revisor é recusado no escalonamento, com evento próprio.
- Fixture de CLI que sai 1 imprimindo `SIMULANDO FALHA XYZ`: a mensagem de falha da task contém
  `SIMULANDO FALHA XYZ`, e o código continua sendo `AGENT_ERROR`.
- Para o mesmo provider com `installed: true` e `ready: 'unknown'`, sidebar, CLI e dashboard
  imprimem `INSTALLED` — os cinco estados do contrato em
  `packages/schemas/src/api/provider-health.ts:91-97`, com teste que prende a tabela copiada.

**Lote 2.** `origin/main` contém `extensions/` e o `package.json` de `main` inclui `extensions/*`
nos workspaces. Existe uma PR fechada com check verde. Um push que quebre `verify` é recusado pela
proteção de branch. `npm run vscode:package` produz o VSIX sem nome fixo no script.

**Lote 3.** Numa máquina limpa, com a extensão instalada e **sem** o monorepo clonado, um
observador cronometra uma pessoa que nunca viu o repositório: abrir uma pasta com repositório git,
`Agentic: Initialize Project`, Start, Nova Mission, aprovar e **observar pelo menos um despacho
real** — evento `attempt.started` com provider real — em menos de quinze minutos, sem abrir
terminal e sem consultar documentação. Contam-se, como medida, os passos de terminal e as edições
manuais de YAML que ainda tenham sido necessários. Além disso: a sonda de ABI reprova um Node
incompatível apontando o driver que a CLI de fato usa; e, sem rede, a extensão ainda encontra uma
CLI já instalada.

**Lote 4.** Reiniciar uma mission cuja worktree anterior foi preservada leva a task a `BLOCKED`
com o motivo do `WorkspaceError` em no máximo cinco tentativas de despacho — verificável pelo
evento, não por observação de tela. Nesse mesmo cenário, o motivo de espera exibido cita
`workspace-acquired`, e não "aguardando vaga". O comando de limpeza devolve o projeto a um estado
em que o run seguinte despacha. Um stop com trabalho em voo não estoura o prazo do cliente antes do
servidor, medido com um planejamento pendurado. Em `win32` a extensão emite o aviso de limitação na
ativação.

**Lote 5.** Um bump de versão altera um arquivo de entrada e propaga para todos os manifestos, e o
empacotamento é reproduzível por um comando único, sem editar nome de arquivo à mão.

## 10. Estratégia de testes

Deliberadamente mais econômica que a das missões anteriores, e declarada antes de começar.

**Durante o desenvolvimento:** testes direcionados aos arquivos tocados, `typecheck`, `lint` e
build da extensão. Nada de regressão completa por commit.

**No fim de cada lote:** `npm run verify` uma vez, mais os testes direcionados do lote. A suíte de
navegador e a de integração da extensão entram só quando o lote tocou a UI ou o ciclo de vida —
hoje elas não estão em gate nenhum e dependem de alguém lembrar; o Lote 1 as coloca em um job
manual ou noturno, não no caminho de cada PR.

**Antes do corte:** `verify` completo, `test:e2e`, suíte de navegador, integração real da extensão
e uma rodada de dogfooding. Só aqui se paga o custo inteiro.

**Regra de teste novo:** só entra teste que prenda um defeito observado ou uma decisão que a
revisão apontou. Teste sem defeito real por trás fica de fora, por política.

## 11. Estratégia de dogfooding

Três projetos, escolhidos para descobrir atrito diferente:

1. **O próprio Desenvolvimento Agêntico.** É o único com gates maduros e o único onde os dois
   primeiros caminhos de busca da CLI existem. Serve para regressão, não para medir onboarding.
2. **Um projeto Node/TypeScript externo**, sem `.agentic`, iniciado do zero pela extensão. É o
   teste real dos Lotes 2 e 3: se o `init` visual e a CLI instalada sob demanda não bastarem, é
   aqui que aparece.
3. **Um projeto real distinto**, de outra natureza e com gates próprios que não seguem a convenção
   npm assumida pelo template (`apps/cli/src/templates.ts:79-87`). O repositório Fluig DevTools,
   que já usa um método agêntico próprio, é o candidato natural: é real, é do mesmo operador e
   tem CI de verdade para comparar.

Em cada um, a medida é a mesma e é observada, não estimada: quantos passos de terminal foram
necessários, quantas edições manuais de YAML, quantas mensagens de erro exigiram abrir um arquivo
de log, e quanto tempo até o primeiro run real. Sem benchmark sintético.

## 12. Estratégia de release

**Uma versão só para core e extensão.** O VSIX não embute a CLI, então a extensão só funciona
contra um core específico: números independentes anunciariam uma liberdade de compatibilidade que
não existe. Nada em `packages/` é publicado hoje, então não há consumidor externo que justifique
cadências separadas. Uma versão significa uma tag, um CHANGELOG e uma release por corte — que é
exatamente o que falta.

**Caminho:** `0.3.0-alpha.1` ao fim do Lote 3 (primeira versão que alguém de fora consegue
instalar), `0.3.0-beta.1` ao fim do Lote 5 com o dogfooding externo feito, e `0.3.0` quando os
critérios de aceitação dos cinco lotes estiverem verificados. Alpha e beta continuam pré-releases
no GitHub, sem Marketplace.

**`1.0.0` fica reservado** para quando houver compromisso público de compatibilidade, não apenas
maturidade interna. Concretamente: formato de mission com `apiVersion` estável e caminho de
migração declarado, superfície da CLI e protocolo entre extensão e core com garantia de
compatibilidade e política de depreciação escrita. Maturidade de uso — revisão cruzada real com
dois fornecedores, ressalvas abertas fechadas — é condição necessária, não suficiente. Não é este
ciclo.

Se e quando a extensão for ao Marketplace, a convenção de pré-release de lá é rotulagem de
publicação, não uma segunda linha de versão.

## 13. Riscos

| Risco | Efeito | Mitigação |
| --- | --- | --- |
| Publicar a CLI em npm exige nome, org e uma decisão irreversível de nome público | trava o Lote 3 | decidir o nome no início do Lote 1, antes de o lote começar; o caminho offline por detecção continua existindo |
| A CLI publicada e o monorepo divergirem | usuário externo roda um core diferente do testado | versão fixada pela extensão e uma única fonte de versão (item 20); a compatibilidade é checada na partida |
| Instalação sob demanda falhar atrás de proxy ou TLS corporativo | primeira partida quebra em ambiente de empresa | manter a detecção como caminho offline e dizer, na mensagem de erro, como apontar uma CLI existente |
| Promover 91 commits para `main` de uma vez | uma PR grande demais para revisar de verdade | a PR documenta que o conteúdo já passou por gates e revisão independente; a CI do Lote 1 é o que passa a valer daqui para frente |
| Windows continuar quebrado enquanto a extensão sugere que funciona | perda de confiança | declarar a limitação no Lote 4; a rota de encerramento no servidor (item 26) fica para depois |
| Escalar `workspace-acquired` para `BLOCKED` mascarar uma causa transitória | task bloqueada sem necessidade | teto de tentativas, não uma; motivo preservado; `task unblock` continua sendo o destravamento |

## 14. Backlog adiado

**Encontrado pela revisão do Lote 1**, registrado e não priorizado:

- **A sonda de provider e o agente real não recebem o mesmo ambiente.** A sonda preserva
  `USERPROFILE`, `SystemRoot`, `TEMP` e `TMP` (`packages/agent-runtime/src/probe.ts`),
  enquanto o despacho usa a allowlist menor de `gates.env.allow`
  (`packages/orchestrator/src/engine/control-plane.ts`). Em Windows uma CLI autenticada por
  `USERPROFILE` pode passar na sonda e perder o ambiente ao executar — o `init` afirmaria uma
  prontidão que o primeiro run não reproduz. Não é regressão deste lote, e Windows já está
  declarado como limitação no Lote 4; o conserto natural é unificar a allowlist e vem junto.
- **`claims` é persistido sem redação.** `failureReason.detail` passou a ser redigido e
  limitado neste lote, mas `attempt.claims.summary/detail` guarda a saída da CLI como veio
  (`packages/providers/src/outcome.ts`, `claimsFromOutput`). O vazamento é limitado (banco
  local, gitignored, e o dashboard é localhost) e tem teto de 400/8000 caracteres, mas existe.
  O conserto exige a redação canônica atravessar a fronteira `providers` — hoje ela vive em
  `process` e em `orchestrator`, em cópias —, o que é ADR, não conserto de lote.
- **Flake na suíte de navegador.** `resolutions.spec.ts` reprovou uma vez em suíte completa
  (dois nós 32px fora do canvas em 1366x768) e passou isolada e na repetição da suíte inteira.
  Enquadramento inicial medido cedo demais, provavelmente; a suíte não está em gate nenhum.

Registrado, não priorizado: smoke de execução real por provider (item 24); `runId` no nome da
branch de tentativa, que resolveria a raiz de P5 mas mexe também no integrador (item 25); rota de
encerramento no servidor (item 26); publicação da CLI em npm como distribuição adicional, depois de
o runtime relocável existir (item 27); automação de release por tag (item 22), cortada por custar
mais que itens de produto sem mudar nada para o usuário; editor visual de mission; higiene das 40 branches locais e das
10 worktrees vivas; e o `MEDIUM` residual do pacote de contexto agentic — sem `--candidate`, um
`HEAD` descendente sai `0` também em papel de revisão. Este último **não pertence a esta versão**:
é ferramenta de workflow interno de outro repositório, não afeta nenhuma jornada do produto, e a
exatidão do alvo já é obtida passando o parâmetro. Vai para backlog.

Também adiado, por serem evolução e não entrada: múltiplos providers com especialização, phase
gates, integração com issues e PR, templates de missão, métricas históricas e custo por task.

## 15. Primeiro lote de implementação

**LOTE 1 — O primeiro run não mente.** É o primeiro porque concentra a maior dor por unidade de
trabalho, não depende de nada e é quase todo de esforço baixo. Ordem sugerida:

1. `init` passa a escrever `.agentic/.gitignore` com `state.db*`, `control-plane.json`,
   `control-plane.lock.db*`, `runs/` e `worktrees/`, com a mesma flag `wx` dos outros arquivos —
   nunca sobrescrever. É o conserto que hoje só existe como instrução no `TROUBLESHOOTING`, e é o
   que destrava o planejamento em projeto externo.
2. `AGENT_ERROR` passa a carregar a última linha significativa da saída da CLI como detalhe,
   mantendo o código decidido apenas pelo exit. O `claims` continua sendo informação operacional
   que **não** decide transição — vale um comentário explícito no código, porque a fronteira é
   invariante do produto.
3. Template do `init`: `project.name` vem do nome da pasta; o registry é montado a partir do que
   foi observado `READY`; o `mock` sai do registry quando há CLI real e, quando não há, a última
   linha do `init` nomeia a troca de `providers.default`.
4. Escalonamento recusa provider `inprocess` como revisor de tentativa real (U12).
5. `gates.yaml` deixa de presumir npm: detectar do projeto ou perguntar; nunca inventar.
6. Sidebar passa a usar os cinco estados do contrato, com teste que prende a tabela copiada.

Ao fim do lote: `verify` uma vez, mais os testes direcionados, e a verificação manual do critério
de aceitação num diretório temporário. Nenhum item deste lote depende de CI, de `main` ou de
empacotamento — por isso ele vem antes deles.
